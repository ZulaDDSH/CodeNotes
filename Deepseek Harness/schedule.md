# schedule code notes

## packages/schedule/schedule/src/runtime.ts:ScheduleRuntime::drive (issue 32)

A task whose target restore, enqueue, Session flush or receipt commit failed stays due, but `drive` excluded it from the next-timer computation, so nothing re-armed the scheduler once the transient fault cleared; only an unrelated change or a Host restart retried it.

Fix: `deliverDue` already returns the still-due failed ids. `drive` now arms a retry timer for them with bounded exponential backoff (`RETRY_BASE_MS` doubling to `RETRY_MAX_MS`), tracked per task (`ScheduleRuntime::backOff`; the finding 362 entry below replaces the shared streak). Every failed attempt is logged by `deliverDue` (`schedule: reminders [...] were not acknowledged`), which is the persistent signal operators see while the streak grows.

At-least-once: a failure after the message was enqueued (flush or commit) leaves that message in the target inbox with no saved receipt, so the retry enqueues the occurrence again. This is the same duplicate the documented crash-before-receipt window produces; the occurrence time is unchanged on retry because it is derived from the task record, not the attempt.

## packages/schedule/schedule/README.md and src/runtime.ts:ScheduleRuntime::deliverDue (issue 63)

Receipt semantics are unchanged: `deliverDue` enqueues, flushes, then commits the receipt, so two boundaries remain. A crash or failed write between flush and receipt re-delivers the occurrence (the issue 32 retry shares this duplicate). Graceful disposal of the target Agent cancels its unclaimed inbox after the receipt, so the task reads as delivered although the message never ran. Closing the second boundary needs a durable occurrence identity plus separate admission, cancellation and execution tracking across Session logs, which is a storage redesign rather than a bounded fix; the limitation is stated precisely in the package README and left in place.

## packages/schedule/schedule/src/runtime.ts:ScheduleRuntime::runNow, ScheduleRuntime::deliverDue, ScheduleRuntime::recoverOutstandingExecution (issue 125)

A `new` target used to skip the execution-slot hold that reused targets take, so a run that outlasted `newSessionIntervalSeconds` (or never finished) let every later occurrence launch another Session, Agent and model stream. The interval bounded launch rate, not concurrent work or cost.

Default chosen by the lead, not yet confirmed by Nomad: every `new` task holds its slot until the Agent of its latest launched Session reaches whole-agent idle, so a task has at most one active run. The three `kind !== 'new'` filters (`runNow`, `deliverDue`, `recoverOutstandingExecution`) are removed, so `new` rides the path reused targets already use. While the slot is held `drive` skips the task, run-now returns `admitted: false`, and the catalog reports `executionActive`. Occurrences that fall due meanwhile coalesce: when the Agent goes idle, `watchExecution` re-drives and `resolveRecurringOccurrence` delivers the latest due occurrence only, the same collapse of missed occurrences late deliveries already get. After a Host restart `recoverOutstandingExecution` re-holds the slot when the last launched Session still has the reminder queued; it cannot know a mid-run Agent, because running state is not persisted (same ceiling as reused targets).

Not implemented: a Host-wide cap across tasks and a configurable per-task limit. A config field would need generated catalog entries, so the limit is fixed at one and the README limitations state the absence of a Host-wide cap.

`packages/schedule/schedule/src/domain.ts:decodeRRuleScheduleRecord`: finding 360 changed the normalized RRULE text to write INTERVAL, COUNT, and BY list numbers without leading zeroes or a plus sign, so a record stored before the change with a padded number would no longer equal its normalization and, because a malformed record refuses the whole Schedule domain, would block Host open; decoding therefore accepts a stored rule that differs from its normalization only by numeric padding (`withoutNumericPadding`) and returns the canonical text, which the next write persists, while a rule over `RRULE_MAX_LENGTH` is refused as invalid like any other corrupt rule.

`packages/schedule/schedule/src/update.ts:createScheduleRecord` and `packages/schedule/schedule/src/update.ts:updateScheduleRecord` (finding 361): a prompt over `MAX_SCHEDULE_PROMPT_BYTES` (65536 UTF-8 bytes) is refused with `invalid_prompt` at creation and at an edit that supplies a prompt. The size check lives only in `createScheduleRecord`; the timing-change and resume paths build through `buildScheduleRecord`, so a task saved before the limit with a larger stored prompt can still be retimed or resumed, and its prompt is left unchanged.

`packages/schedule/schedule/src/delivery-history.ts:appendDelivery` (finding 361): retained history is bounded by bytes as well as age and count. The byte budget counts each distinct prompt text once, not once per receipt that names it, so a task that repeats one prompt keeps its receipts up to the record cap. After the day and record limits, the oldest receipts are dropped until the unique retained prompt text is at most `MAX_HISTORY_PROMPT_BYTES` (1 MiB), always keeping the newest receipt. Dropping marks the history pruned and earlier records unavailable, as the count cap does. Snapshots that no retained receipt names are dropped with them. Per-prompt reference counts are kept incrementally, so the pruning loop is linear in the record count. `packages/schedule/schedule/src/delivery-history.ts:appendDelivery` rebuilds the appended receipt from its four receipt fields, so a caller-supplied extra key such as an inline `prompt` never reaches the stored record or `lastDelivery`.

`packages/schedule/schedule/src/storage.ts:scheduleTaskSchema` (finding 361, prompt snapshots): a receipt no longer copies the sent prompt into every entry. `deliveryHistory.prompts` maps the SHA-256 hex of each sent prompt text to that text once; each history record names its prompt with `promptId`. A task that repeats one prompt therefore stores one copy plus small receipts. A record written with an inline `prompt` is read as migrated: the transform moves the text into `prompts` under the same id, and the next write stores that shape. Reads alone never write. `lastDelivery` never carries `promptId`, so the refine tying it to the latest record strips `promptId` before comparing. A record may name only a prompt the snapshot map holds, and may not carry both an inline `prompt` and a `promptId`.

`packages/schedule/schedule/src/delivery-history.ts:deliveryHistoryPage` (finding 361): pages resolve `promptId` to the snapshot text and return the same `prompt` field as before, so the public history shape is unchanged.

`packages/schedule/schedule/src/runtime.ts:ScheduleRuntime::drive`: finding 362 showed that the Host-wide FIFO (`transact`) was held across target activation, `recoverOutstandingExecution`, Session creation and the Session flush, so one activation or flush that never settled queued every create, edit and delete and every later reminder behind it, and disposal waited for it. The drive loop now runs outside the queue and enters it only for short sections through `exclusive` (storage-only or synchronous work): the due scan, the `new` target reservation commit (`reserve`), the staging step (revalidate, then `followup` and `whenIdle` capture) and the receipt commit. Activation, Session creation, Workspace attach, recovery and the flush run outside it, each raced by `bounded` against `DELIVERY_STEP_TIMEOUT_MS` (120 s, a module constant rather than a Config field, so no generated catalog entry) and, before a message is enqueued, against the runtime stop signal that `dispose` aborts. A step that loses the race fails the delivery, which retries through the existing bounded backoff; the abandoned provider promise is left to settle on its own because activation and flush cannot be cancelled. Due groups then dispatch separately (`packages/schedule/schedule/src/runtime.ts:ScheduleRuntime::dispatch`, finding 362 remaining part, below), so a stalled group no longer delays later due groups of the same drive either.

`packages/schedule/schedule/src/runtime.ts:ScheduleRuntime::drive` and `ScheduleRuntime::dispatch` (finding 362, remaining part): the drive loop awaited each due group in turn, so a group whose activation or flush stalled held every later due reminder until its 120 s deadline, and a reminder that fell due during the stall was delivered late. `drive` now only scans, then starts each due group through `dispatch` and returns; `dispatch` runs `deliverDue` inside its own `withoutInitiator` scope, records the group in `dispatching`, tracks the promise in `deliveries` (drained by `dispose`), and on completion removes the group and calls `requestDrive`, which recomputes the timer. A task is eligible for the scan only when `eligibleAt` (its scheduled occurrence, its delivery floor and its retry time) has passed and it is neither executing nor dispatching, so a task mid-activation is never started twice and an in-flight task does not produce a zero-delay timer. Failures back off per task (`ScheduleRuntime::backOff`, the same 5 s doubling capped at 5 min, keyed by task instead of by drive pass), and a committed receipt clears the task's retry entry. Deliveries run concurrently only up to `MAX_CONCURRENT_DELIVERIES` (16): at startup with many overdue groups, the first 16 activations start at once and the rest start as each settles, so a large backlog cannot open an unbounded number of Session restores; while at the cap `drive` skips the timer because any completion re-drives. Keeping at-least-once semantics: the message is still enqueued and flushed before the receipt commits, and the revalidation at staging is unchanged. The removal of the global `failureStreak` means one permanently failing task no longer slows the retry of an unrelated task.

`packages/schedule/schedule/src/runtime.ts:ScheduleRuntime::deliverDue`: every slow step now runs against a task value captured earlier, so the queue sections revalidate before acting. Staging requires each member to deep-equal its captured value (`isDeepStrictEqual` over the whole stored task, which covers status, rule, target, `pendingDelivery` and `lastDelivery`) and not to be in `executing`; a task that was edited, paused, deleted or delivered by a concurrent manual run is dropped without a failure, and the edit's own `requestDrive` schedules the next scan. `executing` is only added to inside a queue section (or synchronously in recovery, which re-checks it after activation), so `drive` and `runNow` cannot both enqueue one occurrence. The message text is built from the staged value after revalidation, so an edit made during activation is never delivered stale. Two checks keep their earlier purpose without inline comments: members are filtered as due before target resolution so a target made future by clock rollback creates no Session, and again at staging because Session restoration can span a rollback, where future members keep their timer obligation; a failure keeps timer obligations for members that were already committed or made future by rollback.

`packages/schedule/schedule/src/runtime.ts:ScheduleRuntime::commitMember`: the receipt commit runs after the flush and revalidates against the current row. A deleted task gets no commit (the message is already enqueued and persisted) and its slot is released at once; a task retargeted during the flush still records the receipt and advances through `keepTarget`, which keeps the new target and its own `pendingDelivery`, because skipping the commit would leave the occurrence due and deliver it again to the new target; a task whose status or rule (title and prompt aside) changed during the flush receives the receipt only through `delivered`, never `advanced`, so a pause is not undone and a reschedule is not overwritten; an unchanged task advances exactly as before, and a title or prompt edit made during the flush is kept. The occurrence carried by the message is fixed at staging, so occurrence identity does not depend on how long the flush took. The at-least-once boundary of finding 32 is unchanged: a flush deadline after `followup` leaves the message in the inbox with no receipt, and a retry can enqueue the occurrence again, the same outcome as a flush that rejects.

`packages/schedule/schedule/src/runtime.ts:ScheduleRuntime::bounded`: activation steps reject immediately when the runtime stops, because nothing has been enqueued; every rejection of `bounded` is a `DeliveryStepAbandonedError`, which `recoverOutstandingExecution` rethrows instead of treating as "no outstanding delivery", since delivering anew while the earlier message may still sit in the inbox would enqueue a second copy. The flush of an already enqueued reminder (`enqueued`) instead gets `STOP_FLUSH_GRACE_MS` (5 s) after the stop signal, so disposal still drains an accepted delivery through its receipt commit, as the runtime contract says, but never waits out a stalled flush. `packages/schedule/schedule/src/index.ts:ScheduleService::serialize` takes a `draining` flag that the runtime queue uses so those receipt commits are not refused once the service is stopping; the service awaits `runtime.dispose()` before it awaits the chain and closes the domain, so every queued commit lands first. `runNow` refuses new work when stopping itself, because the queue no longer does, and `dispose` awaits every in-flight manual run (`manual`) because a run no longer sits on the service chain that shutdown drains.

`packages/schedule/schedule/src/runtime.ts:ScheduleRuntime::runNow`: a manual run uses the same staging and commit sections, so a slow activation no longer holds the queue; it returns the `admitted: false` result when the task changed, entered `executing` or entered its delivery floor while its Session was being activated, and `undefined` when it was deleted. The occurrence is sampled in the staging step, after Session restoration, which can take longer than one recurrence interval. The caller's `AbortSignal` is checked at each queue entry; it does not interrupt an activation already in flight, which the deadline bounds. `enqueue` captures the target Agent's `whenIdle()` immediately after `followup`, because waiting for the durable flush can miss the whole lifecycle of a fast target Agent.

`packages/schedule/schedule/tests/update-service.spec.ts` (edit during the delivery flush): the earlier test required an edit to wait behind the whole delivery commit and then conflict. That ordering is exactly the head-of-line blocking of finding 362, so an edit made while a flush is pending now applies at once and the later receipt commit keeps it (title edit) or only records the receipt (pause or reschedule).

`packages/schedule/schedule/tests/targets.spec.ts:wakes the idle earlier Session of a new-Session task and still launches the due occurrence` (finding 362): the launch after the idle boundary runs from a zero-delay timer that `ScheduleRuntime::dispatch` arms once its `finally` clears `dispatching`, one hop after the idle callback re-drives. The test therefore advances 10 ms after the 1000 ms wait. The launch rule itself is unchanged.

`packages/schedule/schedule/tests/runtime.spec.ts:batches same-Session recurring tasks once while keeping other Session obligations separate` (finding 362): due groups now activate concurrently, so `followup` order follows activation timing rather than store order. The test picks each message by its reminder text and compares the resolved Session ids as a set.

`packages/schedule/schedule/tests/runtime.spec.ts:drains the deliveries in flight at disposal and arms no timer` replaces the earlier "stops between committed tasks" case. Both due one-shot tasks enter `ScheduleRuntime::deliverDue` in the same drive pass, so disposal finds the second commit already in flight. Disposal drains it, as `ScheduleRuntime::dispose` promises for accepted deliveries, and the drive loop's `stopping` check keeps any group not yet dispatched from starting. The assertion is the drain plus no remaining timer, not one commit.

`packages/schedule/schedule/tests/stalled-delivery.spec.ts:bounded concurrent deliveries` (finding 362): 17 unrelated groups whose activations never settle; the first 16 start together and the 17th starts only after one of them reaches the 120 s step deadline, which pins `MAX_CONCURRENT_DELIVERIES` at 16.
