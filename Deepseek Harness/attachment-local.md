# attachment-local code notes

`packages/attachment/attachment-local/src/file-quota.ts:FileStoreQuota`: verbatim files had no size limit and nothing deleted them, so any caller of `saveFile` / `saveFileStream` (an upload route, including a LiveShare reader holding `fileUploads/upload`) could fill the host volume (finding 30). The quota refuses one file above `maxFileBytes` and refuses growth of `file-objects/` above `maxStoredFileBytes`. Usage is scanned once from `file-objects/` on first use, then updated when an upload publishes a digest that did not already exist; bytes of in-flight uploads are reserved chunk by chunk so concurrent uploads cannot jointly overshoot, and are released when the upload finishes or fails. Streamed bodies are refused while streaming, so an oversized upload never completes its staging file. Re-uploading an existing digest consumes no quota when the whole body is in memory (`saveFileVerbatim` checks existence before reserving); a streamed body is metered before its digest is known, so a duplicate that does not fit in the remaining room is still refused. Automatic garbage collection is not implemented: resumed and forked Sessions share objects and no reference model exists yet, so unreferenced objects stay until an operator deletes them.

`packages/attachment/attachment-local/src/file-store.ts:saveFileStreamVerbatim`: takes an optional quota; `existsSync` on the digest path inside `targetFor` decides whether the published object is new for quota accounting. A concurrent identical upload can be counted twice, which only errs towards refusing.

`packages/attachment/attachment/src/error.ts:ATTACHMENT_ERROR_CODES`: `FILE_TOO_LARGE` (one file above the backend's per-file limit) and `FILE_STORE_FULL` (the backend's total file budget is exhausted) are raised by the local backend and reach the browser as the `reason` of `session/attachment-invalid`; the Web UI has no dedicated text for them and shows its generic send-failed text with the code.

`packages/attachment/attachment-local/src/index.ts:LocalAttachmentStore.requestVersion`: request-image generation is shared per variant id, which digests the attachment id and target only, so concurrent callers with the same bytes but different display metadata (name, `originalDimensions`) share one generation. The shared result now carries the verified reference of the caller that started it, so each caller gets its own reference back after it is checked against the shared one for attachment id, media type, byte count and dimensions; a mismatch raises `ATTACHMENT_CORRUPT` instead of returning another occurrence's reference (finding 354).

`packages/attachment/attachment-local/src/compression-limiter.ts:CompressionLimiter.run`: takes an optional signal and the task's input bytes; a task still waiting for a slot is removed from the queue when the signal aborts (and one already aborted never queues), so cancelled work never retains its inputs or runs later. A task that already started keeps running because the image library offers no cancellation. Finding 355 asked for a bound on waiting work: `CompressionLimiter.admit` refuses a group of tasks with `IMAGE_QUEUE_FULL` when the tasks that would wait exceed `queue.tasks` or their summed bytes exceed `queue.bytes`, and `run` applies the same check to a single task. The queue is therefore bounded, not merely its active part.

`packages/attachment/attachment-local/src/index.ts:LocalAttachmentStore` (constructor): the queue limits are `QUEUED_IMAGE_BATCHES` (2) times the resolved `maxImagesPerMessage` and `maxMessageImageBytes`, derived from the configured image limits rather than fixed numbers. Any batch the image limits admit therefore fits an empty queue, and at most two full batches wait at once; a third concurrent batch is refused. No new Config field is added, so no generated catalog entry changes.

`packages/attachment/attachment-local/src/index.ts:LocalAttachmentStore.saveImages`: the whole batch is admitted before any member is queued, so a refused batch leaves nothing behind. The per-batch signal is aborted by a member that fails, which drops the batch's queued members, and each member checks the signal before it starts preparing so a late-starting member of a failed batch never begins. A member already inside `prepareImageFile` runs to completion (`store.ts` has no checkpoint inside the decode and encode, and the image library cannot be interrupted). Finding 355 remains partial for that active stage only.

`packages/attachment/attachment-local/src/store.ts:inspectMetadata`: an animated source image (more than one frame) is refused with `INVALID_IMAGE` instead of being normalized to its first frame, because the durable still reference and the model replay cannot show later frames and the composer gave no warning. Conservative default for finding 356: refuse rather than silently flatten; a single-frame GIF is unaffected and still re-encoded, and the user can attach the animation as a file. `detectImage` and `canPassThroughNormalization` still report animation so the refusal stays at the admission boundary.

`packages/attachment/attachment-local/src/store.ts:ensureDurableDirectory`: the `chmod(0700)` now applies only to store-owned directories (staging and object buckets); `ensureDurableHome` passes `restrict: false`, so a pre-existing user-selected harness home keeps its mode bits (group access, setgid) while a home the store creates is still made with mode `0700` by `mkdir`. The durability sync walk is unchanged and independent of the mode change (finding 351).

`packages/attachment/attachment-local/src/index.ts:LocalAttachmentStore.fileHostPath`: the path handed to the model as a verbatim read-only copy was derived from the reference without touching disk, so a deleted or resized object produced a handle describing bytes that were gone. The method now returns `undefined` (the request projection's no-path handle) unless the stored alias exists and has the referenced byte count. This is a synchronous existence and length check only: it does not hash the file (a file can be 1 GiB), and it cannot bind the verified bytes to the later tool read, so same-length changes and a change after the check are not detected; the integrity-checked stream remains `readFileStream`. Finding 349 is partial; routing model file reads through an integrity-checked capability needs a design decision outside this package. Images keep `imageHostPath` unchanged because it is a pure derivation relied on by other callers.

`packages/attachment/attachment-local/src/request-image.ts:readCached`: a cache entry was accepted after a header probe, so any other decodable image with compatible format, colour, alpha and bounds (a same-shaped or smaller replacement) was returned under the original variant id. Each entry now has a `<hash>.sha256` sidecar holding the digest of the cached bytes, written after the entry; a read whose sidecar is missing (entries from before this change) or does not match the bytes regenerates the entry from the verified source. This detects corruption, partial writes and replacement of the image alone; it is not authentication, so someone who can rewrite both files can still plant an image. The variant id remains a digest of the inputs, not of the output, so a remote upload index keyed by it (`llm-deepseek/src/file-store.ts`) is not made byte-exact by this change (finding 353 partial).

`packages/attachment/attachment-local/src/store.ts:publishStagedObject`: releases the in-process staging registration as soon as the staging name is unlinked, so a completed publication never shields a later crash residue from the sweep (finding 352).

`packages/attachment/attachment-local/src/store.ts:ensureDurableHome`: finding 351 check. A pre-existing user-selected harness home keeps its mode bits; the contract is covered by `tests/store.spec.ts` with an explicitly chmodded home (POSIX only; Windows has no mode bits to compare).

`packages/attachment/attachment-local/src/request-image.ts:readCached`: finding 353 residual. The sidecar digest (see the earlier note) detects corruption and single-file replacement of a cached variant, and the test now covers same-length corruption of pixel data as well as same-shaped and smaller replacements. Residual: the sidecar and entry live in the same user-owned cache directory, so a writer that can replace both files still plants an image; authenticating that would need a trust anchor outside the cache (a per-home secret readable by the same user does not stop it), and the only fully closing option is regenerating every request from the verified original. This is recorded as a decision for NOMAD; the upload identity is now byte-exact (see `llm-deepseek/src/file-store.ts:uploadIdentityOf`).

`packages/attachment/attachment-local/src/file-store.ts:verifiedStoredFilePath`: finding 349 completion. The earlier size-only check in `LocalAttachmentStore.fileHostPath` let a same-length rewrite of a stored file reach the model as a host path. The host path is now offered only after the file on disk hashes to the reference digest and byte count. Hashing runs synchronously in bounded chunks because the `fileHostPath` contract returns a string synchronously; the result is cached per path by stat identity (device, inode, size, mtime, ctime) so each model request does not rehash large files. The cache is bounded by entry count. A rewrite that lands between the verification and the model's own read is not covered; the check narrows the window but cannot close it, and the package README states this.

`packages/attachment/attachment-local/src/index.ts:DEFAULT_MAX_FILE_BYTES`: no longer exported. The plugin entry exports only the Loader four and the Service classes; the default byte limits are read only inside this module's own config defaults, and no other package imports them. The gate `verify-plugin-entry-exports` rejects value exports beyond the Loader four.

`packages/attachment/attachment-local/src/index.ts:DEFAULT_MAX_STORED_FILE_BYTES`: no longer exported, for the same reason as `DEFAULT_MAX_FILE_BYTES`.

### `packages/attachment/attachment-local/src/store.ts:reclaimAbandonedStaging`
Finding 352 (supersedes the earlier sweep notes). A staging file is named `<ownerPid>-<uuid>`. The sweep runs on every staged write, not once per process, so residue from a sibling process that crashed is reclaimed while the host keeps running. Liveness is decided by the owner, not by age: a file owned by this process is live only while it is in `activeStaging`; a file owned by another pid is live while `process.kill(pid, 0)` succeeds or fails with EPERM, whatever its mtime, and is reclaimed at once on ESRCH. A bare-UUID name (written before this change, no owner recorded) keeps the 24 h mtime rule. A recycled pid only delays reclaim of a dead writer's file; it can never delete a live writer's file. The sweep returns the files and bytes it removed.
