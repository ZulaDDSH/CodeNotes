# office-kit code notes

## Release fences saves (finding 83)

- `packages/document/office-kit/src/outputs.ts:OutputStore::reserve` - a reservation names an owner and is taken BEFORE the conversion is queued (`OfficeKit::convertTo` and `recalculate` take it before `queue.read`), because the queue wait and the conversion take seconds while the save takes milliseconds. `release(owner)` marks every open reservation of that owner released at once and waits for each to finish, so a conversion that completes after the release can no longer register an output for that owner.
- `packages/document/office-kit/src/outputs.ts:OutputStore::save` - uses the caller's reservation, or a private one when none is passed so a direct save is fenced too. `saveNow` checks the reservation and the caller signal before the write (a queued or late save writes nothing) and again after it (a save paused inside the write deletes what it wrote and rejects). A reservation taken after the release belongs to a new generation, so a later Session that reuses the owner id keeps its outputs.
- `packages/document/office-kit/src/index.ts:OfficeKit::convertTo` - finishes the reservation in a `finally`, so a failed or cancelled conversion never leaves a release waiting; `recalculate` does the same.
- Not verified: whether Session disposal aborts the tool signal that tool-office passes to `convertTo`. The reservation does not depend on it.

## Parsing runs in a kit helper, not in the Host process (finding 81)

- `packages/document/office-kit/src/index.ts:OfficeKit::runOperation` - traced `@deepseek-ai/libreoffice-kit` 0.2.3 `lib/index.js`: the conversion path runs `runWorker` (a Node `Worker` thread in the Host process that validates the OOXML archive, resolves fonts and, for WASM, converts) and then, for native engines, `runNative` / the image path, which call `spawnNative` (`child_process.spawn`) so the LibreOffice engine loads the document in a disposable helper child process. So on Windows and macOS the native parser is NOT inside the Host process; on Linux the WASM engine runs in a Worker thread of the Host process (WASM memory isolation, no native code). The kit README says the same: "A render creates a separate native process or Node worker and private profile".
- Bounds already enforced for every parse: `timeoutMs` (deadline in the helper, killed on expiry), `maxInputBytes` and the `maxSourceBytes` reservation (checked before the bytes are read), `maxOutputBytes`, and for OOXML `maxArchiveEntries` and `maxUncompressedBytes`; `tests/provider.spec.ts` "passes configured limits to the kit" proves the provider forwards them.
- Remaining limit, not fixable in this package: the helper inherits the Host's token and Job restrictions (the kit documents "inherit the caller's token and Job restrictions"), so it is not filesystem- or network-confined, and the kit exposes no memory cap or spawn wrapper. Legacy binary `.doc`/`.xls`/`.ppt` have no entry or decompression caps (only the size and time bounds). Confining the helper needs a spawn-wrapper or restricted-token option in the kit.

## A reader whose result copy fails settles with that error (finding 388)

- `packages/document/office-kit/src/queue.ts:ConversionQueue::finish` - same defect as office-to-pdf: the reader was released before `copyOutput`, so a copy that threw left that reader unsettled; the copy now runs first and the reader is released only after it succeeds, so `fail` rejects it.
- `packages/document/office-kit/src/queue.ts:ConversionQueue::readStored` - alias hits copy before reader admission and consume no reader slot, as `packages/document/office-kit/README.md` documents; the aggregate delivery bound is not enforced by the queue (the caller and the transport hold the copy). Not changed (finding 388, aggregate half). `packages/document/office-kit/src/index.ts:OfficeKit::render` Remote tracking (`remoteRequests`) is not capped for the same reason: the copy outlives the call.

## Cancelled saves stop evicting older outputs (finding 419)

- `packages/document/office-kit/src/outputs.ts:OutputStore::saveNow` - the signal already reached the save (`OutputStore::save` passes it, and `saveFile` forwards it) and was checked before eviction and after the write, so a save cancelled while queued or while writing evicted nothing or removed its own file. The gap was the eviction loop: each deletion is awaited with no re-check, so a cancellation during one deletion still evicted every older output the save needed. The loop now re-checks the reservation and signal before each deletion and again after the loop, before the write, so a cancelled save evicts at most the one deletion already in progress.
- `packages/document/office-kit/src/index.ts:OfficeKit::convertTo` - the report's "cancellation after publication leaves an unreported file" sub-claim is not fixed here. After `saveNow` records the entry and checks the signal, control returns through promise continuations only (`saveFile`, `convertTo`, `convertFile`, the tool's `execute`, then the pipeline's `signal.aborted` check) with no I/O between them, so a cancellation cannot land in that window without a macrotask boundary, which this chain does not have. Verified by reading the chain, not by a test.

## Waiting saves are bounded by bytes (finding 420)

- `packages/document/office-kit/src/outputs.ts:OutputStore::save` - a save used to join the serial chain with no admission check, so each waiting save pinned its complete output buffer while converters kept releasing their reader slots. `save` now counts the bytes of every unsettled save (waiting, writing, or evicting) in `pendingBytes` and refuses a save with `busy` when it would push that total past `maxBytes`, the store's existing budget, so no new config key is needed. Outputs larger than `maxBytes` still fail as `output-too-large` from `saveNow`. The count is released when the save settles, on success or failure.
- `packages/document/office-kit/src/outputs.ts:OutputStore::save` - the check runs before the private reservation is created, so a refused save leaves no reservation behind. Cancellation already removes queued saves through `throwIfStale` in `saveNow`, but the buffer stays referenced by the chained closure until its turn; that residual is not changed.
- Decision: the default bound is the store's `maxBytes` (512 MiB by default), which is as large as the retained-file budget. A smaller bound would need a config key and a schema change; not made here.
