# tool-executor-ptc code notes

`packages/core/tool-executor-ptc/src/ptc.ts:binding` (finding 52): a binding returned the tool's value to the program with no byte bound, so one large result (or many concurrent ones) was copied into the runtime transport and the worker before the program could produce any capped output. The binding now measures the returned JSON value with `jsonByteSize`, an allocation-free walk that stops as soon as it passes the limit, and rejects the call with a program-visible error when the value exceeds `Config.maxBindingResultBytes` (default 16 MiB) or when the run's cumulative delivered bytes would exceed `Config.maxProgramResultBytes` (default 64 MiB). The rejected call still settles and is logged as a normal dispatch (the log content goes through the spill listener), so the Session log shows the tool succeeded while the program saw `ToolCallError`. Program image bindings return an attachment reference, not the value, and are not counted.

The bound is enforced at the executor, after the tool produced its value: the Host has already allocated it, so this stops the copy into the transport and the worker and the accumulation of delivered values, but it does not stop a tool from allocating a large result. Bounding production needs each tool's own output cap. The count is an estimate of the JSON text length (UTF-8 string bytes plus structural overhead), not an exact serialization size, and the aggregate counts bytes handed to the program over the run, not bytes the program still retains, because the executor cannot observe when the program drops a value. Streaming or paged bindings for large values are not implemented.

`packages/bundle/base/cordis.patch.yml:tool-executor-ptc` (PTC default): the base bundle mounts `tool-executor-ptc` enabled and keeps `tool-executor-native` as a `disabled: true` row. Both ids stay so existing overlays (`apps/cli/config/examples/ptc.yml`, the snapshot patches) that name either row keep composing, and `apps/cli/config/examples/native.yml` is the opt-out. Exactly one executor row may be enabled per scope, so every override swaps both rows.

`packages/bundle/acp-app/cordis.patch.yml:tool-executor-native` (ACP pin): the ACP bridge projects only top-level `tool/call` and `tool/result`, while nested `run_code` calls log `tool/ptc-dispatch` events with ids `<parent>:ptc:<n>`. A nested permission request would therefore name a tool call id the client never saw, so acp-app stays native until the bridge projects nested dispatch events.

`packages/bundle/sdk-minimal/cordis.patch.yml:tool-executor-native` (standalone): sdk-minimal mounts no PTC runtime, and `run_code` needs `@deepseek-ai/dsh-ptc-runtime-node`, so it stays native by design.

`apps/web/tests/scaffold.ts:tool-executor-native` (test pin): scaffolded web tests, the keyless SDK e2e files, and the snapshot base compositions pin native because their recorded provider responses script direct tool calls and cannot be re-recorded without a provider key; the `ptc-*` scenarios and `packages/bundle/web-app/tests/tool-executor-default.spec.ts` cover the PTC default.

`packages/core/tool-executor-ptc/src/index.ts:PtcExecutor.describe` (unconfined host): a program has full Node authority, so the runtime never runs it unconfined; `sandbox-unavailable` stays a fail-closed result. `ptc.ts` sets `PtcCalls.confinementUnavailable` when the default `run_code` transport reports that kind, and `PtcExecutor.describe`, the `tools:ptc-only` and `tools:sdk` sections and the `reject` hook read it, so from the next model step every tool is presented and callable directly and only the shell stays closed, as under the native executor. The latch is per executor and not set for registered program tools, because `createRunCodeTool` builds its own `PtcCalls`. A startup probe cannot replace it: the Windows runner is a sole candidate selected without a probe (`sandbox-local:PLATFORM_CHAINS`), so only execution reveals a failure.

`packages/ptc-runtime/ptc-runtime-node/src/worker.ts:Worker.start` (latch spoofing): the exit handler classifies runner failures from the process's stderr, which a started program also writes, so it only applies `classifyRunnerFailure` while `ready` is false. The readiness handshake precedes every program dispatch, so a refusal before it comes from the runner or bootstrap and a program cannot forge it. `ToolExecutor.describe` takes the pre-restriction known names as an optional second argument (`packages/core/tools/src/index.ts:ToolsService`), which `PtcExecutor.describe` returns with `run_code` appended after the latch so a `toolOrder` that names `run_code` or a restricted tool still validates.

`packages/acp/acp/src/session.ts:AcpSession` (decision, ACP nested `tool/ptc-dispatch` events not projected): Question: should the ACP bridge learn `tool/ptc-dispatch` and `tool/ptc-dispatch-start` so nested PTC calls are announced to ACP clients? Why it matters: a nested call still passes the approval pipeline, so under PTC a client would see a permission request for a tool call id it was never told about. Options: (1) teach the bridge to project the nested events; (2) keep `acp-app` on the native executor and leave the bridge top-level only. Decision: option 2. Verified 2026-11-24: `packages/bundle/acp-app/cordis.patch.yml:tool-executor-native` enables native and disables `tool-executor-ptc`; `packages/bundle/sdk-minimal/cordis.patch.yml:tool-executor-native` mounts only native and no `ptc-runtime`; `packages/acp/acp/src/session.ts` reacts only to `assistant/message`, `tool/call` and `tool/result` and has no `ptc` reference; `packages/bundle/web-app/tests/tool-executor-default.spec.ts` asserts `acp-app` is `{ native: true, ptc: false }`. So no PTC program runs behind the bridge and the projection code would be dead until `acp-app` opts in. Revisit trigger: `acp-app` (or a deployment overlay on it) enabling `tool-executor-ptc`; the bridge change and the bundle change must land together. Blocks nothing.

`snapshots/sdk/text-turn/cordis.yml:tool-executor-native` (decision, snapshot corpus not re-recorded under PTC): Question: should the replay snapshot corpus be re-recorded under the default PTC executor? Why it matters: the corpus is the only end-to-end replay of model-visible requests, so it decides whether default-bundle behaviour is covered. Options: (1) re-record all scenarios under PTC; (2) keep the corpus pinned to native and cover PTC with dedicated scenarios. Decision: option 2. Verified 2026-11-24: 51 files under `snapshots/` (the `cordis.yml` / `runtime.cordis.yml` of the session, sdk and acp scenarios) carry the row pair `tool-executor-ptc` disabled and `tool-executor-native` enabled under the comment "the recorded corpus replays native tool calls"; the headless `*-snapshot.patch.yml` profiles under `apps/cli/tests/profiles/headless/` pin the same way; the fixtures hold recorded native tool-call turns, re-recording needs a provider key, and pinning keeps them independent of the code-mode prompt and `run_code` schema, which would otherwise rewrite every fixture on a prompt edit. PTC itself is covered by `snapshots/sdk/ptc-turn`, `snapshots/sdk/ptc-cancel`, `snapshots/sdk/cua-run-code`, `snapshots/sdk/desktop-ptc-context` and `packages/bundle/web-app/tests/tool-executor-default.spec.ts`. Revisit trigger: a snapshot that is meant to cover default-bundle behaviour (for example a model-visible tool listing of the shipped composition); add it as a PTC scenario instead of flipping the corpus.

`packages/core/tool-executor-ptc/src/ptc-calls.ts:PtcCalls.confinementUnavailable` (decision, one-step cost on unconfined hosts accepted): Question: should the executor probe confinement at startup so a host without it never pays a failed `run_code` step? Why it matters: on such a host the first `run_code` returns `sandbox-unavailable`, costs one extra model step, and only then does the latch make every tool callable directly. Options: (1) startup probe; (2) accept the one-step cost per executor lifetime. Decision: option 2, no probe. A startup probe cannot see the failure on the Windows runner (a sole candidate selected without a probe that refuses only when it executes), and running programs unconfined is rejected because programs have full Node authority. The latch (`packages/core/tool-executor-ptc/src/index.ts:PtcExecutor.describe`) lasts for the executor's lifetime, so the cost is one step per session on hosts without confinement and none elsewhere. Revisit trigger: telemetry showing that this step cost matters. Pinned by `packages/core/tool-executor-ptc/tests/ptc.spec.ts`.
