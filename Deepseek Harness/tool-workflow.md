# tool-workflow code notes

## Oversized results are saved to the spill store (finding 96)

- `packages/workflow/tool-workflow/src/index.ts:saveOversizedResult` - `renderResult` clipped the pretty-printed JSON at `maxResultChars` and the omitted tail was unreachable by the model. When the rendering is longer than the cap, the complete pretty-printed JSON is now saved through `ctx.spillStore.saveText()` (the `packages/fs/tool-fs-search/src/search-core.ts:trySaveFormattedResult` pattern: owner is the calling agent's session header id, source is the tool call, best effort; a missing backend or a rejected save logs a warning and leaves the plain truncation notice). The foreground value carries the reference as the optional output field `spill` (`locator`, `bytes`, `retrievalHint`) and `renderResult` appends `Full result stored at: <locator>. <hint>` after the truncation notice. The background path saves in the settle path of `packages/workflow/tool-workflow/src/index.ts:startBackgroundRun` (through `jobOutcomeOf`) and puts the same footer in the job `result` text, which is a string, so it has no `spill` field.
- `packages/workflow/tool-workflow/src/index.ts:SpillSaver` - a minimal structural type instead of importing `@deepseek-ai/dsh-spill`: adding that dependency (package.json, tsconfig reference, `node_modules` link) would change the lockfile, which is out of bounds for this change. The `spillStore` service is looked up opportunistically with `ctx.get('spillStore')` through a cast because the `Context` declaration merge lives in dsh-spill and is not in this package's program. The save request mirrors `SaveTextSpill`; if that type changes, `SpillSaver` must follow. A deployment needs a spill backend (`dsh-spill-local`) for the handle to exist; without one the behaviour is the previous truncation.
- The saved text is the JSON value only (not the `workflow "<name>" completed` header), so the artifact is directly parseable.
- `packages/workflow/tool-workflow/src/index.ts:exceedsCap` - the save is awaited only when the rendering exceeds the cap. An unconditional `await` on a small result adds microtask ticks to `execute` and reorders the `run-end` records of concurrently settling runs (`records zero-member and concurrent runs independently` caught this).

## A member-record failure no longer drops the run's terminal record (finding 390)

- `packages/workflow/tool-workflow/src/index.ts:createWorkflowRecorder` previously removed the run from `active` when an `agent-start` or `agent-end` append failed, so `finish` found no session and never appended `run-end`. The run then stayed in the durable log as started with no terminal record, and the panel rendered it as running for as long as its Turn was not interrupted or forked.
- The recorder now keeps the run in `active` and records the failed member position in `memberRecordingStopped`. Later member events for that run are skipped, which avoids an orphan `agent-end` after a lost `agent-start`, and `finish` still appends `run-end`. `abandon` and `finish` clear the run from both sets.
- The prefix contract changes for two positions: a failed `agent-start` now yields `run-start, run-end`, and a failed `agent-end` yields `run-start, agent-start, run-end`. A failed `run-start` still records nothing, and a failed `run-end` still leaves the run without a terminal record. These two are not fixed here and stay documented limits.
- Decision: the narrow fix is the recorder-side terminal append. Persisting a separate recording-health flag or reconciling against the background job outcome would change the durable event schema, so it is left for a later pass; the panel's `incomplete` status from finding 389 covers the member side.
- Covered by `packages/workflow/tool-workflow/tests/tool-workflow.spec.ts:isolates a first append failure` (the `it.each` over the four record types, whose prefix expectations were updated for the two member positions). Background runs use the same recorder and are not separately exercised by this test. Reload behaviour is not tested here.
- The limit text in `packages/workflow/tool-workflow/README.md` (Known Limitations, the durable-records bullet) now states the member-failure behaviour and the remaining run-end limit.
