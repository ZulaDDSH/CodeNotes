# attachment-local code notes

`packages/attachment/attachment-local/src/file-quota.ts:FileStoreQuota`: verbatim files had no size limit and nothing deleted them, so any caller of `saveFile` / `saveFileStream` (an upload route, including a LiveShare reader holding `fileUploads/upload`) could fill the host volume (finding 30). The quota refuses one file above `maxFileBytes` and refuses growth of `file-objects/` above `maxStoredFileBytes`. Usage is scanned once from `file-objects/` on first use, then updated when an upload publishes a digest that did not already exist; bytes of in-flight uploads are reserved chunk by chunk so concurrent uploads cannot jointly overshoot, and are released when the upload finishes or fails. Streamed bodies are refused while streaming, so an oversized upload never completes its staging file. Re-uploading an existing digest consumes no quota when the whole body is in memory (`saveFileVerbatim` checks existence before reserving); a streamed body is metered before its digest is known, so a duplicate that does not fit in the remaining room is still refused. Automatic garbage collection is not implemented: resumed and forked Sessions share objects and no reference model exists yet, so unreferenced objects stay until an operator deletes them.

`packages/attachment/attachment-local/src/file-store.ts:saveFileStreamVerbatim`: takes an optional quota; `existsSync` on the digest path inside `targetFor` decides whether the published object is new for quota accounting. A concurrent identical upload can be counted twice, which only errs towards refusing.

`packages/attachment/attachment/src/error.ts:ATTACHMENT_ERROR_CODES`: `FILE_TOO_LARGE` (one file above the backend's per-file limit) and `FILE_STORE_FULL` (the backend's total file budget is exhausted) are raised by the local backend and reach the browser as the `reason` of `session/attachment-invalid`; the Web UI has no dedicated text for them and shows its generic send-failed text with the code.

`packages/attachment/attachment-local/src/index.ts:LocalAttachmentStore.requestVersion`: request-image generation is shared per variant id, which digests the attachment id and target only, so concurrent callers with the same bytes but different display metadata (name, `originalDimensions`) share one generation. The shared result now carries the verified reference of the caller that started it, so each caller gets its own reference back after it is checked against the shared one for attachment id, media type, byte count and dimensions; a mismatch raises `ATTACHMENT_CORRUPT` instead of returning another occurrence's reference (finding 354).

`packages/attachment/attachment-local/src/compression-limiter.ts:CompressionLimiter.run`: takes an optional signal and the task's input bytes; a task still waiting for a slot is removed from the queue when the signal aborts (and one already aborted never queues), so cancelled work never retains its inputs or runs later. A task that already started keeps running because the image library offers no cancellation. Finding 355 asked for a bound on waiting work: `CompressionLimiter.admit` refuses a group of tasks with `IMAGE_QUEUE_FULL` when the tasks that would wait exceed `queue.tasks` or their summed bytes exceed `queue.bytes`, and `run` applies the same check to a single task. The queue is therefore bounded, not merely its active part.

`packages/attachment/attachment-local/src/index.ts:LocalAttachmentStore` (constructor): the queue limits are `QUEUED_IMAGE_BATCHES` (2) times the resolved `maxImagesPerMessage` and `maxMessageImageBytes`, derived from the configured image limits rather than fixed numbers. Any batch the image limits admit therefore fits an empty queue, and at most two full batches wait at once; a third concurrent batch is refused. No new Config field is added, so no generated catalog entry changes.

`packages/attachment/attachment-local/src/index.ts:LocalAttachmentStore.saveImages`: the whole batch is admitted before any member is queued, so a refused batch leaves nothing behind. The per-batch signal is aborted by a member that fails, which drops the batch's queued members, and each member checks the signal before it starts preparing so a late-starting member of a failed batch never begins. A member already inside `prepareImageFile` runs to completion (`store.ts` has no checkpoint inside the decode and encode, and the image library cannot be interrupted). Finding 355 remains partial for that active stage only.

`packages/attachment/attachment-local/src/store.ts:inspectMetadata`: an animated source image (more than one frame) is refused with `INVALID_IMAGE` instead of being normalized to its first frame, because the durable still reference and the model replay cannot show later frames and the composer gave no warning. Conservative default for finding 356: refuse rather than silently flatten; a single-frame GIF is unaffected and still re-encoded, and the user can attach the animation as a file. `detectImage` and `canPassThroughNormalization` still report animation so the refusal stays at the admission boundary.

`packages/attachment/attachment-local/src/store.ts:ensureDurableDirectory`: the `chmod(0700)` now applies only to store-owned directories (staging and object buckets); `ensureDurableHome` passes `restrict: false`, so a pre-existing user-selected harness home keeps its mode bits (group access, setgid) while a home the store creates is still made with mode `0700` by `mkdir`. The durability sync walk is unchanged and independent of the mode change (finding 351).

`packages/attachment/attachment-local/src/index.ts:LocalAttachmentStore.fileHostPath`: returns a verified private handoff copy (see `host-file.ts:handoffStoredFile`) or `undefined` when the file is above `maxHostPathVerifyBytes`, missing, resized, or fails its digest; it never returns the shared alias. `readHostFile` is the matching seam for in-process readers. `imageHostPath` follows the same rule through `host-file.ts:handoffStoredImage`: it returns a verified private copy named `<digest>.<ext>` in the same handoff directory, or `undefined` when the object is missing, fails its digest or exceeds `maxHostPathVerifyBytes`. Callers must tolerate `undefined` (`llm/src/content.ts:resolveImageAttachmentAccess` already does). The first call per image copies the object synchronously.

`packages/attachment/attachment-local/src/store.ts:publishStagedObject`: releases the in-process staging registration as soon as the staging name is unlinked, so a completed publication never shields a later crash residue from the sweep (finding 352).

`packages/attachment/attachment-local/src/store.ts:ensureDurableHome`: finding 351 check. A pre-existing user-selected harness home keeps its mode bits; the contract is covered by `tests/store.spec.ts` with an explicitly chmodded home (POSIX only; Windows has no mode bits to compare).

`packages/attachment/attachment-local/src/index.ts:DEFAULT_MAX_FILE_BYTES`: no longer exported. The plugin entry exports only the Loader four and the Service classes; the default byte limits are read only inside this module's own config defaults, and no other package imports them. The gate `verify-plugin-entry-exports` rejects value exports beyond the Loader four.

`packages/attachment/attachment-local/src/index.ts:DEFAULT_MAX_STORED_FILE_BYTES`: no longer exported, for the same reason as `DEFAULT_MAX_FILE_BYTES`.

### `packages/attachment/attachment-local/src/store.ts:reclaimAbandonedStaging`
Finding 352 (supersedes the earlier sweep notes). A staging file is named `<ownerPid>-<uuid>`. The sweep runs on every staged write, not once per process, so residue from a sibling process that crashed is reclaimed while the host keeps running. Liveness is decided by the owner, not by age: a file owned by this process is live only while it is in `activeStaging`; a file owned by another pid is live while `process.kill(pid, 0)` succeeds or fails with EPERM, whatever its mtime, and is reclaimed at once on ESRCH. A bare-UUID name (written before this change, no owner recorded) keeps the 24 h mtime rule. A recycled pid only delays reclaim of a dead writer's file; it can never delete a live writer's file. A file named for this process's own pid that is not registered in `activeStaging` is live only while its mtime is newer than the 24 h cutoff, so residue of a crashed earlier process that received the same pid is reclaimed once it ages out. The sweep returns the files and bytes it removed.

### `packages/attachment/attachment-local/src/request-image.ts:readCached`
Finding 353 (supersedes the earlier sidecar notes). The request-image cache directory is writable by anything running as the harness user, so no value stored beside the entry, a digest sidecar or a keyed MAC whose key lives on the same disk, can prove who produced the bytes: a writer who can replace the entry can replace its proof. The trust anchor is therefore process memory. `trustedVariants` maps each cache path to the SHA-256 of the bytes this process generated and wrote (`writeCached`); a cache read is accepted only when the bytes it just read hash to that digest, and the verified bytes it hashed are the bytes it returns, so nothing can change between check and use. An entry with no in-memory digest (written by an earlier process, or planted before this process wrote it) is regenerated from the verified source attachment and overwritten. The disk file stays only so a process does not hold every variant in memory; it is a spill, not a persistent cache. Cost: the first request for each variant after a process start regenerates once; the map holds at most `TRUSTED_VARIANT_LIMIT` entries and an evicted variant is regenerated on its next request. The `.sha256` sidecar is removed. The remote upload index is byte-exact through `llm-deepseek/src/file-store.ts:uploadIdentityOf`, which keys reuse by the variant id plus the output digest.

### `packages/attachment/attachment-local/src/host-file.ts:handoffStoredFile`
Replaces the removed `file-store.ts` functions `verifiedStoredFilePath` and `rememberSavedFile`, which statted a path, reopened it by path to hash it, cached the identity of the first stat (so a swap in between was trusted), and returned a path the model's tools opened later with no check. No saved-file identity from a path stat is recorded any more.
Finding 349 completion for readers that open a path themselves (shell, PTC, office). `fileHostPath` no longer returns the shared alias under `files/`: it copies the alias into a private handoff directory and returns that copy. The copy is made from one descriptor: the alias is opened once, and every chunk read from that descriptor is hashed and written to the copy in the same loop, so the bytes the copy holds are exactly the bytes that were hashed. A digest or length mismatch discards the copy and withholds the path. The copy is created `wx` with mode 0600, then made read-only (0400; the read-only attribute on Windows), inside a 0700 directory `attachments/v1/handoff/<ownerPid>-<uuid>/<sha256>/<name>`, which is private to the owning process (the brief asked for per-session; the store has no session identity at `fileHostPath`, so the unit is the process that owns the store). The directory is removed when the store's Cordis fiber disposes, and a later store removes directories whose owner pid has exited (the same liveness probe as the staging sweep). On Windows no ACL is set explicitly: `DSH_HOME` is user-profile-private and the directory inherits it. A reused copy is trusted only while the identity taken from a descriptor opened on it (device, inode, size, mtime, ctime) is the one recorded when it was built. Files above `maxHostPathVerifyBytes` get no handoff path (the copy is a synchronous read of the whole file), including files this process just saved. Threat model: an attacker running as the same user can rewrite the copy or the whole store and is outside it, exactly as for the request-image cache (finding 353); the guarantee is that a storage change or corruption after the handoff cannot alter what the model's tools read, and that the handed-out bytes equal the referenced digest.

### `packages/attachment/attachment-local/src/host-file.ts:readStoredHostFile`
Finding 349 verified-read seam. `AttachmentStore.readHostFile(hostPath, maxBytes, signal)` resolves `undefined` for a path that is not one of the store's own (`objects/`, `file-objects/`, `files/`, `handoff/` below the versioned root), so callers read it normally. For a store path it opens the file once, reads at most `maxBytes` from that descriptor while hashing, and returns the bytes only if the digest named by the path matches; a mismatch is `ATTACHMENT_CORRUPT`, an open failure is `ATTACHMENT_NOT_FOUND` or `ATTACHMENT_READ_FAILED` (never a fallback to an unverified read, which would reopen the window), and a file above `maxBytes` or the store's `maxHostPathVerifyBytes` is `FILE_TOO_LARGE`. The path shape (kind, digest position) is checked before anything touches the disk, so reads of ordinary files cost no `realpath`; only a path of store shape that is not under the root as given is matched against `realpath(root)`. Matching is case-folded on Windows. The returned bytes are the bytes hashed, so nothing can change between check and use.

### `packages/attachment/attachment-local/src/host-file.ts:releaseHandoffs`
Removes the owning store's handoff directory when its Cordis fiber disposes and forgets the recorded identities; `reclaimAbandonedHandoffs` removes sibling directories named `<pid>-<uuid>` whose pid no longer exists (finding 349). It runs once per store before the first copy. It skips directories of live owners and the directories this process registered when it made its first copy (`liveHandoffDirectories`); an unregistered directory carrying this process's own pid is a crashed earlier run with a recycled pid and is removed.
