# desktop code notes

`apps/desktop/src/mandatory-update-policy.ts:DesktopMandatoryUpdatePolicy`: the policy started every process unblocked and was not persisted, so a restart cleared a known mandatory-update block and, when the policy service was unreachable or demanded fresh authentication, the failure preserved the new unblocked state. The constructor now accepts an optional `DesktopPolicyStore`; a mandatory decision (40005) is written to it when received, and the next process seeds its state from it so protected actions stay blocked until a fresh valid no-force response clears the record. The record is bound to the policy origin and the installed bundled dsh version, so an installed update (a different version) or a different deployment ignores a stale record and relies on the launch check. Offline recovery policy: there is none beyond that; an unreachable service keeps the block, and only a fresh no-force response or an installed version change releases it. The file is user-writable and is a durability aid, not a security boundary: deleting it clears the block, as would editing the product itself. Covered by `apps/desktop/tests/mandatory-update-policy.spec.ts`.

`apps/desktop/src/mandatory-update-policy.ts:fileDesktopPolicyStore`: reads tolerate a missing or corrupt file (treated as no record) and writes go through a temporary file and rename; write failures are swallowed because losing persistence must not break the in-process block.

`apps/desktop/src/file-actions.ts:installFileActions`: finding 311 showed that a direct download reserved its destination with an exclusive empty file, closed the handle and later removed that pathname when the download was cancelled or interrupted, so a file another process had moved into place after the reservation was deleted, including after a navigation cancellation had already retired the request. The reservation now records the device and inode of the file it created, and cleanup (`removeReserved`) removes the path only while it is still a regular file with that identity; a missing or replaced file is left alone. The check and the removal are two calls, so a replacement created between them is still not detected; a private staging file with an atomic publish would close that window and was not built. Covered by `apps/desktop/tests/file-actions.spec.ts`.

`apps/desktop/src/file-actions.ts:installFileActions`: finding 312 showed that the startup timeout stopped once Chromium announced the download, so a transfer that began and then went silent kept the request pending for the window's lifetime. A transfer inactivity timer (`DSH_DESKTOP_FILE_DOWNLOAD_STALL_TIMEOUT_MS`, default 300000 ms) now starts when the download starts in direct mode and is restarted by every `updated` event; on expiry the request rejects with a stalled error, the item is cancelled and the reservation cleanup runs from the `done` event. In save-as mode the timer arms on the first `updated` event only, because the native save dialog has no application deadline and a user choosing a path must not be reported as a stalled transfer; an `updated` event is taken to mean the dialog has closed (UNVERIFIED against Chromium, not run in a real Electron process). Covered by `apps/desktop/tests/file-actions.spec.ts`.

`apps/desktop/src/file-drag.ts:installDesktopFileDrag` (finding 310): a resource drag no longer lends the live source path to the operating system. `prepare` reads the authorized file once with `verifiedBytes`, which rejects a size mismatch or a SHA-256 that differs from the Host digest, and stages those same bytes through `DragFiles.prepare`. The OS receives only that private copy, so a source modified, replaced or removed after the drag starts cannot change what the receiver reads. The bytes are held in memory during the read, and the copy counts against the 64 MiB aggregate budget in `apps/desktop/src/file-drag-files.ts:DragFiles`. A resource larger than that budget returns no preparation, and the renderer falls back to its URL read. `borrow`, the borrowed-version check at drag start and the `sameVersion` comparison were removed as dead code. Covered by `apps/desktop/tests/file-drag.spec.ts`.

`apps/desktop/scripts/desktop-policy-environment.mjs:resolveDesktopPolicyEnvironment`: an unsigned Windows build had no update source, because `createElectronBuilderConfig` passed `publish: null` and no `app-update.yml` was written, which disables `UpdateCoordinator`. The owner decided those builds get a real https feed served from GitHub releases and no mandatory-update service exists for them. Setting `DSH_DESKTOP_UPDATE_FEED_URL` therefore makes the resolver return `undefined`, so no `dshMandatoryUpdatePolicy` is embedded and the packaged app runs without a policy (`resolveDesktopPolicyConfig(undefined)` returns `undefined`). The callers (`electron-builder-config.mjs:createElectronBuilderConfig`, `desktop-package-environment.mjs:validateDesktopPackageEnvironment`) already tolerate that result. Covered by `apps/desktop/tests/desktop-policy-environment.spec.ts`.

`apps/desktop/scripts/desktop-policy-environment.mjs:resolveDesktopUpdateFeedUrl`: validates the feed (https, no credentials, query or fragment, trailing slash because the generic provider joins `<channel>.yml` onto it) and rejects it for signed builds, since a signed build would silently lose its mandatory policy while still requiring the COS settings. `createElectronBuilderConfig` turns it into `publish: [{ provider: 'generic', url, channel }]`, which electron-builder writes to `resources/app-update.yml` and which electron-updater's generic provider reads. `validateDesktopPackageEnvironment` calls it too so `--check` rejects a bad value. `loadDesktopPackageEnvironment` rejects the variable for darwin, and local unsigned macOS builds never read the dotenv, so the variable only affects Windows. Covered by `apps/desktop/tests/installer-packaging.spec.ts` and `apps/desktop/tests/desktop-package-environment.spec.ts`.

`apps/desktop/scripts/publish-github-feed.mjs:rewriteFeedMetadata`: the feed lives in a rolling prerelease `desktop-feed` that holds only `nightly.yml`, while installers and blockmaps live in per-version releases `v<version>`. `/releases/latest/download` cannot serve this because every release is a prerelease, and electron-updater's github provider does not match these tags, so the generic provider reads `https://github.com/<repo>/releases/download/desktop-feed/<channel>.yml`. The script uploads the same rewritten metadata as both `nightly.yml` and `stable.yml`, because the channel chosen in Settings (`updater.channel`) selects the file name; Stable and Nightly are therefore the same build on this feed. electron-builder writes relative file names, so the script rewrites every `files[].url` and `path` to the absolute asset URL under `releases/download/v<version>/`; the generic provider resolves absolute URLs unchanged and follows GitHub's 302 redirect to the CDN. GitHub renames assets whose names contain characters outside letters, digits, dot, underscore and hyphen, so any other name is rejected rather than linked. `publishGithubFeed` uploads installer and blockmap first and the two metadata files last, so a client never sees metadata for an asset that is not yet downloadable; a failed versioned upload aborts before the feed is touched. The `--clobber` replacement is not atomic, so a client fetching mid-replacement can get a 404 and retries at its next check. Unsigned installers have no publisher signature, so the only integrity check is the sha512 in the metadata and anyone with release write access can ship code to these clients. UNVERIFIED end to end: no packaged app has updated from this feed yet. Covered by `apps/desktop/tests/publish-github-feed.spec.ts`.
