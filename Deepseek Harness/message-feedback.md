# message-feedback code notes

`packages/feedback/message-feedback/src/index.ts:MessageFeedbackService.put`: a per-message rating could not be kept on the device, so a note typed into the rating dialog was released to the telemetry collector with the conversation prefix, while `/feedback --local` could keep a remark local. `MessageFeedbackPutRequest.localOnly` now travels on the `feedback/message-put` event (event level, not on the stored item, so the item shape and its version token are unchanged) and the telemetry backend treats such an event as a non-authorizing record. The field is written only when `true`; an absent field is the exported form, so existing logs read the same. `putSchema` accepts the optional boolean, so replaying a log never rejects it. A put that matches the stored rating, note and category stays a no-op and appends no event, whatever `localOnly` says; the stored item does not remember its earlier visibility, so re-submitting an unchanged rating cannot switch an already exported or an already local rating. Covered by `packages/feedback/message-feedback/tests/message-feedback.spec.ts` (local-only cases).

`packages/feedback/message-feedback/src/index.ts:MessageFeedbackService.delete`: withdrawing a rating is itself an export trigger, so the delete request carries the same optional `localOnly` and the `feedback/message-delete` event records it only when `true`; `deleteSchema` accepts it. The flag is not inferred from how the rating was put: the human chooses at the withdrawal confirmation. Covered by the same spec.

## Live feedback writes confirm the durable prefix before a version conflict is returned (finding 416)

- `packages/feedback/message-feedback/src/index.ts:MessageFeedbackService::withSession` appends a live feedback event before flushing it. A failed flush leaves that event in the live Session history, so a retry with the previously observed version used to receive a `version-conflict` carrying the unconfirmed item, and the client adopted it as the saved rating. A live session whose last append was not confirmed is now flushed and checked against the durable log before any write operation runs. If that confirmation fails, the write fails with the persistence error and no conflict is returned. The pending state is tracked per Session in memory, so a restart simply drops the unconfirmed event as before.
- The read path (`list`) is intentionally not gated: it still returns items from the live history, so a list read can show an unconfirmed rating until the next write or a successful flush. This is a known residual; gating reads would turn a transient disk fault into a list failure.
- Covered by `packages/feedback/message-feedback/tests/message-feedback.spec.ts` (a retry that still cannot flush rejects instead of reporting a conflict).

## packages/feedback/message-feedback/src/index.ts:MessageFeedbackService::unconfirmedLive

The set records live sessions whose last feedback append was not yet confirmed durable. It is cleared on `session/disposed` (registered in `[Service.init]`) so a disposed session id never forces a confirmation flush on a later live session that reuses the id.
