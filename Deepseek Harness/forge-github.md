# forge-github code notes

`packages/experimental/forge-github/src/provider.ts:GitHubProvider::act`: a changing `gh` command that timed out or exceeded its output limit was rethrown, so the caller got an exception instead of a result, and a server error (HTTP 5xx) was reported as `failed`, which says nothing changed although GitHub may have applied the request. Both now map to `unknown` (the request was sent, and the answer does not confirm the outcome). `gh` that cannot start stays `failed`, and so do refusals with a 4xx status, a 409 (`stale`) and credential errors (`unauthenticated`) keep their codes. A nonzero exit with no HTTP status stays `failed`; this is an unverified assumption that `gh` does not fail after sending a request without printing a status.

`packages/experimental/forge-github/src/provider.ts:GitHubProvider::rerunChecks`: the loop stopped at the first unexpected failure and reported the rest as a plain `failed`, so a caller could retry the whole set and repeat reruns GitHub had already accepted. Every eligible run is now tried (except after a credential refusal), and each run lands in one of three groups: accepted, refused, or of unknown outcome (timeout, output limit, server error). The result is `undefined` only when every run was accepted. It is `failed` (or `unauthenticated` for a credential refusal) only when no run was accepted and none is of unknown outcome. Otherwise it is `unknown`, since some reruns changed the host and the caller must check it before retrying; the message counts each group. Choosing `unknown` for a partly accepted batch is a decision for the owner: `failed` promises nothing changed, which a partly accepted batch breaks. Cancellation still throws, as the registry contract documents, so the per-run account is lost on cancel.

`packages/experimental/forge/src/index.ts:ForgeService::markReady`: the registry polled a watched change request only after the provider returned, so an action that threw left the watch stale until its regular poll. `markReady`, `merge` and the shared `act` now poll in a `finally`, so the watch refreshes after the host accepted, refused, or failed the action or the provider threw. The shared `act` polls only when the provider has the action, as before. Covered by `packages/experimental/forge/tests/watch.spec.ts`.

Tests for the provider changes are in `packages/experimental/forge-github/tests/provider.spec.ts`, at `GitHubProvider::act` and `GitHubProvider::rerunChecks`.

`packages/experimental/forge-github/src/review-writes.ts:writeGitHubReview`: the head check and the review mutation are two GitHub calls, and GitHub's mutations take no head commit, so a push between the check and the mutation can receive the write on the new head (issues.md finding 385). The check still refuses an already-moved head with `stale`; nothing in the write path makes the check atomic, and the registry does not undo a published write. The contract wording in `packages/experimental/forge/src/types.ts:ForgeReviewWrite` and the provider README now states this race instead of promising that a write never lands after the head moved. No revert-proof test: the change is documentation, and the race needs a live host to reproduce. The head check and the mutation are both in `writeGitHubReview`, so a controlled head-move test would need a fake `gh` that moves the head between its two calls; that test is not written.

`packages/experimental/forge-github/src/viewed.ts:writeViewed`: the same check-then-write race applies to viewed marks. The JSDoc of `writeViewed` already states it; the README line on `setViewed` now states it too.
