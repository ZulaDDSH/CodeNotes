# tool-executor-ptc code notes

`packages/core/tool-executor-ptc/src/ptc.ts:binding` (finding 52): a binding returned the tool's value to the program with no byte bound, so one large result (or many concurrent ones) was copied into the runtime transport and the worker before the program could produce any capped output. The binding now measures the returned JSON value with `jsonByteSize`, an allocation-free walk that stops as soon as it passes the limit, and rejects the call with a program-visible error when the value exceeds `Config.maxBindingResultBytes` (default 16 MiB) or when the run's cumulative delivered bytes would exceed `Config.maxProgramResultBytes` (default 64 MiB). The rejected call still settles and is logged as a normal dispatch (the log content goes through the spill listener), so the Session log shows the tool succeeded while the program saw `ToolCallError`. Program image bindings return an attachment reference, not the value, and are not counted.

The bound is enforced at the executor, after the tool produced its value: the Host has already allocated it, so this stops the copy into the transport and the worker and the accumulation of delivered values, but it does not stop a tool from allocating a large result. Bounding production needs each tool's own output cap. The count is an estimate of the JSON text length (UTF-8 string bytes plus structural overhead), not an exact serialization size, and the aggregate counts bytes handed to the program over the run, not bytes the program still retains, because the executor cannot observe when the program drops a value. Streaming or paged bindings for large values are not implemented.

`packages/bundle/base/cordis.patch.yml:tool-executor-ptc` (PTC default): the base bundle mounts `tool-executor-ptc` enabled and keeps `tool-executor-native` as a `disabled: true` row. Both ids stay so existing overlays (`apps/cli/config/examples/ptc.yml`, the snapshot patches) that name either row keep composing, and `apps/cli/config/examples/native.yml` is the opt-out. Exactly one executor row may be enabled per scope, so every override swaps both rows.

`packages/bundle/acp-app/cordis.patch.yml:tool-executor-native` (ACP pin): the ACP bridge projects only top-level `tool/call` and `tool/result`, while nested `run_code` calls log `tool/ptc-dispatch` events with ids `<parent>:ptc:<n>`. A nested permission request would therefore name a tool call id the client never saw, so acp-app stays native until the bridge projects nested dispatch events.

`packages/bundle/sdk-minimal/cordis.patch.yml:tool-executor-native` (standalone): sdk-minimal mounts no PTC runtime, and `run_code` needs `@deepseek-ai/dsh-ptc-runtime-node`, so it stays native by design.

`apps/web/tests/scaffold.ts:tool-executor-native` (test pin): scaffolded web tests, the keyless SDK e2e files, and the snapshot base compositions pin native because their recorded provider responses script direct tool calls and cannot be re-recorded without a provider key; the `ptc-*` scenarios and `packages/bundle/web-app/tests/tool-executor-default.spec.ts` cover the PTC default.
