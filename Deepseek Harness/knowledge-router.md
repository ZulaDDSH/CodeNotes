
`packages/knowledge/knowledge-router/src/packet.ts:boundItems` (finding 202): bounding shortened and dropped provider items but never touched the task or the fixed header, so a task longer than `maxPacketBytes`, or a cap below the header size, produced a packet whose `bytes` exceeded the advertised bound even with every item gone. The bound is defined as the UTF-8 length of the rendered packet text (`renderPacket`, which is what `bytes` reports); the structured tool result carries the same fields but only the rendered text is the model-facing size. When the empty packet (header plus task) alone exceeds the bound, `boundItems` now throws an explicit error instead of silently truncating the user's task or returning an over-bound packet, so every returned packet satisfies `bytes <= maxBytes`. The earlier test that asserted items are dropped in that situation was changed to expect the error.

`packages/knowledge/knowledge-router/src/memorix-store.ts:memorixRecent` (finding 373): the query matched `entityName` alone, and Memorix stores every project's observations in one database, so a row with the same entity name in another project (for example a legacy entity name shared by two folders) was returned to the caller. The query now takes a required `project` and matches `projectId` in the same SQL statement, so the filter runs in the database before the limit and a project's newest rows are not displaced by another project's. The only caller is the automatic-memory fallback in `packages/client/ui-memory-workspace/src/automation.ts:MemoryAutomation::recent`. The `projectId` column is the same identifier that `memorixStoredChunk` verifies on write.
