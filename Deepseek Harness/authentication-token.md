# authentication-token code notes

`packages/host/authentication-token/src/index.ts:apply` (`publish`, `PENDING_API_PEER_DEADLINE_MS`, `MAX_PENDING_API_PEERS`): a `/connect` exchange creates an API Peer and signs its id into a cookie before any mux socket exists, and only a socket attachment ever disposed it. A caller holding the launch token could exchange repeatedly without attaching and grow the Peer map for the Host lifetime, and cookie expiry never removed the unused record. Each unattached Peer now carries an unref'd deadline timer. When it fires, the credential is revoked (removed from `apiPeers`) before the Peer is disposed, so a later attach with that cookie is refused. At most `MAX_PENDING_API_PEERS` unattached Peers exist at once; `publish` then returns `undefined` and `BrowserAuth::authorizeConnect` answers 503 with `Retry-After` without creating a Peer. The cap is per Host (one launch token, one owner principal), and the limit counts only unattached exchanges, so it does not restrict established sockets.

`packages/host/authentication-token/src/index.ts:apply` (`webserver/upgrade`): the deadline timer is cleared at the moment the mux upgrade is claimed (after the exact-Peer check and the active check), so a socket that attaches just before the deadline owns the Peer through the existing release path and the timer cannot dispose it afterwards. Releasing the Web scope clears every pending timer and disposes the still-unattached Peers.

`packages/host/authentication-token/src/browser-auth.ts:BrowserAuth` (`sessions`, `revoke`, `revokeAll`, `persistSessions`): browser cookies carried only an authority and timestamps, so a copied cookie stayed valid until expiry or key replacement and no single browser could be cut off (finding 114). Each minted browser cookie now carries a random `sid` and the same id is recorded, with authority and expiry, in a `sessions` map that is persisted inside the existing `client-connection/browser-session` grant record next to the secret. `revoke(sid)` moves the id into a persisted `revoked` map (kept until the cookie would have expired) and a cookie whose `sid` is revoked is refused on its next request, also after a restart. Validity is a deny-list, not an allow-list, so a cookie minted by another BrowserAuth instance on the same record (tests, a second plugin generation) still verifies; cookies from before this change have no `sid` and can only be ended by raising `sessionGeneration`. Mint stays synchronous (the response is written at once) and the record write is queued behind earlier ones; a failed write is logged and leaves the session valid until restart. `revokeAll()` and the config field `sessionGeneration` replace the signing secret and clear the map, which is the emergency global revocation: raising `sessionGeneration` and reloading the plugin invalidates every browser and API cookie, because the generation is stored in the record and a mismatch rotates the secret. API (v2) cookies are unchanged: their revocation is the Peer's socket close. Limits for `packages/host/authentication-token/src/index.ts:apply`: the owner-only `/browser-sessions` route (below) is the only operator surface for listing and revoking sessions, and the generation field remains the global lever; a second Host process sharing the same credentials file does not see the other's revocations until it reloads.

`packages/host/authentication-token/src/browser-auth.ts:BrowserAuth.revoke`: `revoke` now returns `Promise<boolean>` and rejects with the credential-store error when persisting the revocation fails, so a caller learns that the revoked cookie would become valid again after a restart; the in-memory revocation still applies. `persistSessions` returns the raw write promise while the internal chain logs and swallows the failure, and the cookie-minting path ignores that rejection. The owner-only `/browser-sessions` route in `packages/host/authentication-token/src/index.ts:apply` is the production caller of `sessions` and `revoke`; `revokeAll` and `settled` still have no production caller.

`packages/host/authentication-token/src/browser-auth.ts:BrowserAuth.persistSessions`: the write replaced the record's `sessions` and `revoked` maps with this instance's in-memory copies, so a write from one instance erased a session or revocation that another instance on the same record had written. A revoked cookie could then verify again after the next persist. The write now runs inside `modifyRecord` against the current record: stored sessions and revocations are unioned with the in-memory maps, a revoked id is removed from sessions, expired entries are pruned, and the merged result is adopted into memory so later revokes and listings see other instances' writes. Revocations only accumulate until they expire, so a later write cannot drop one. Limit: this instance refuses another instance's revocation only after it persists again or reloads, because request verification reads memory and never the store.

`packages/host/authentication-token/src/browser-auth.ts:BrowserAuth.trackSocket`, `BrowserAuth.revoke`, `BrowserAuth.revokeAll`: a revoked browser cookie was refused only on its next HTTP request, so a mux socket already upgraded under that cookie stayed open. Upgrades claimed by the shared browser Peer now register the socket under the cookie's session id (`BrowserAuth.browserSessionId`), and each socket removes itself on close. `revoke(id)` destroys that session's sockets before awaiting the record write, so the in-memory revocation closes the socket even when persistence then fails; `revokeAll` destroys every tracked socket. API (v2) sockets are not tracked here: their revocation is the Peer close already described for `index.ts:apply`.

`packages/host/authentication-token/src/index.ts:apply` (`/browser-sessions` route): the owner-only operator surface. It is an exact route with anonymous admission and its own check, which requires a valid v1 browser cookie through `BrowserAuth.isAuthenticated`, so an API v2 cookie cannot list or revoke browser sessions and a caller without a browser cookie gets 401. GET returns the live session ids with authority and expiry. POST with a bounded JSON body `{ id }` revokes that id (404 when unknown, 400 for a malformed body, 405 for other methods). The session id travels in the body, not the path, so it is not written into request logs as a URL.
