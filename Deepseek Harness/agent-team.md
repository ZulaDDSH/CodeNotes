# agent-team code notes

## packages/team/agent-team/src/index.ts:TeamService::recoverHistoricalMessage (issue 69)

Older Team sessions hold `team/message/queued` records, acknowledged by `team/message/delivered`. The current runtime sends peer messages through the subagent inbox and never reads the old mailbox, so an unacknowledged record was stranded and no API could say what became of it. The projection already exposes these as `historicalMessages[].delivered === false`; `TeamService::pendingHistoricalMessages` lists them for the Lead.

`recoverHistoricalMessage` is the deliberate decision for one such message, made by the Lead only. `discard` appends the existing `team/message/delivered` acknowledgement so the record leaves the pending view; nothing is sent. `replay` first checks the target Session for a user message that already carries the matching `team-message` source (a delivery whose acknowledgement was lost); if found it only acknowledges. Otherwise it sends the content through `subagents.sendMessage`, prefixed with a line naming the original sender, then appends the acknowledgement and flushes. Each call runs inside the Lead's journal transaction, and a message that is no longer pending returns `already-resolved`, so repeating a call is safe.

Limit: a crash after the send and before the acknowledgement is flushed leaves the message pending, and a later replay sends it again (at-least-once). The sender-source check cannot see the new inbox delivery because the subagent runtime stamps its own source. A target that cannot be reached makes `replay` throw and leaves the message pending, so the Lead can discard it instead.

`packages/team/agent-team/src/index.ts:TeamService.setEnabled`: finding 275. The selection is appended and applied before the flush, and the Boolean the flush returns (false when no durability listener participated) was ignored, so a mode change could report success with no confirmed persistence, while a thrown flush surfaced a bare persistence error that did not say the selection is already live. A rejected or non-participating flush now throws `TEAM_MODE_PERSISTENCE_UNCONFIRMED` whose message names the live mode and says to repeat the same selection to retry (the appended event is kept and repeating it only flushes, as before). The browser panes already display the Remote error message and the disable confirmation already retries the same call; a dedicated same-selection retry button on the switch pane is not added (limit).

`packages/team/agent-team/src/index.ts:TeamService.setEnabled`: finding 275 (Gateway follow-up). `setEnabled` threw a plain `TeamError`, which the Gateway's `rpcFailure` does not recognize (it only passes values carrying the Remote marker), so the client received `gateway/internal` and the browser's `TEAM_MODE_PERSISTENCE_UNCONFIRMED` check never matched. The unconfirmed case is now a `RemoteError` with the same code, and its details carry the live mode. The code string is unchanged; its `RemoteErrorDetailsMap` entry is declared in `packages/team/agent-team/src/types.ts`, which `src/client.ts` re-exports, so the client compilation sees the code. Limit: the generated `lib/typert.host.js` is untracked build output and is regenerated by the package build, not committed.

### `packages/team/agent-team/src/index.ts:TeamService.setEnabled`

Finding 275, restart behaviour. An appended `team/mode` event reaches the Session log through two independent writers: the `session/flush` call that `setEnabled` awaits, and the persistence backend's own bounded batch timer plus its drain on handle close. A flush that rejects or resolves `false` therefore does not mean the event is absent from disk. `packages/team/agent-team/tests/persistence.spec.ts` pins three outcomes against the real JSONL backend. (1) An unconfirmed flush followed by a graceful stop: the resumed Session reads the mode as applied, with exactly one `team/mode` event, and repeating the selection appends nothing. (2) The backend write itself failing (`persistBatch` rejecting) through the stop: the resumed Session reads the previous mode, and selecting again appends one event and persists. (3) The retry after a recovered listener, covered in `team.spec.ts`, appends nothing because `setEnabled` only appends when the live mode differs. No source change was needed: the restart test did not expose a bug. A hard process crash between the append and the batch write is the same as case (2); it cannot be exercised in-process.
